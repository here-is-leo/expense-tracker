## استراتژی Branch

1. `main` — نسخه پایدار و محافظت‌شده؛ فقط از طریق Pull Request
2. `develop` — شاخه یکپارچه‌سازی؛ فقط از طریق Pull Request
3. `feature/<name>` — برای قابلیت‌های جدید
4. `fix/<name>` — برای رفع باگ‌ها

## روند کاری

### 1. کار را از `develop` شروع کنید:

```bash
git checkout develop
git pull origin develop
git checkout -b feature/your-feature
```

### 2. کار خود را انجام دهید و با پیام‌های واضح Commit کنید.

### 3. Branch را Push کنید:

```bash
git push -u origin feature/your-feature
```

### 4. در GitHub یک Pull Request به `develop` باز کنید.

### 5. منتظر یک تأیید (Approval) بمانید.

### 6. گزینه Squash and Merge را انتخاب کرده و Branch را حذف کنید.

## استاندارد پیام Commit

فرمت:

```text
<type>: <short description>
```

انواع:

1. `feat:` — قابلیت جدید
2. `fix:` — رفع باگ
3. `refactor:` — تغییر در کد بدون تغییر رفتار برنامه
4. `docs:` — مستندات
5. `test:` — تست‌ها
6. `chore:` — ابزارها، وابستگی‌ها و تنظیمات

مثال:

```text
feat: add user registration endpoint
fix: prevent cross-user transaction access
test: add IDOR authorization test
```

بک‌اند اکنون API کامل MVP را در اختیار دارد و توسعه‌دهنده فرانت‌اند می‌تواند ساخت قابلیت‌های زیر را شروع کند.

## اولویت ۱: رابط کاربری احراز هویت

این بخش برای سایر قسمت‌ها ضروری است.

### 1. صفحه ثبت‌نام (Register)

فیلدها:

* Email
* Display Name
* Password

اعتبارسنجی سمت کلاینت:

* فرمت صحیح ایمیل
* خالی نبودن Display Name
* رمز عبور حداقل ۸ کاراکتر باشد و شامل حداقل یک حرف و یک عدد باشد.

پس از موفقیت:

* `accessToken` ذخیره شود.
* کاربر به Dashboard منتقل شود.

در صورت خطا:

* خطاهای Validation دریافتی از API به‌صورت Inline نمایش داده شوند.

### 2. صفحه ورود (Login)

فیلدها:

* Email
* Password

پس از موفقیت:

* `accessToken` ذخیره شود.
* کاربر به Dashboard منتقل شود.

در صورت خطا:

پیام عمومی زیر نمایش داده شود:

```text
Invalid email or password
```

### 3. مدیریت وضعیت احراز هویت

* Token را در حافظه با React Context یا در `localStorage` برای ماندگاری ذخیره کنید.
* در تمام درخواست‌های محافظت‌شده API، Header زیر را ارسال کنید:

```text
Authorization: Bearer <token>
```

* در صورت دریافت `401`:

  * Token پاک شود.
  * کاربر به صفحه Login منتقل شود.
* هنگام بارگذاری صفحه، در صورت وجود Token در Storage، آن را بازیابی کنید.

### 4. Protected Routes

صفحات Dashboard و Transactions باید با یک Guard محافظت شوند.

اگر Token وجود نداشت، کاربر باید به صفحه Login هدایت شود.

# الزامات مشترک

## API Client

یک ماژول واحد برای API Client ایجاد کنید که:

* Base URL را از متغیر محیطی بخواند، برای مثال:

```text
VITE_API_BASE_URL
```

* به‌صورت خودکار Bearer Token را اضافه کند.
* خطای `401` را مدیریت کند:

  * Auth State را پاک کند.
  * کاربر را به Login منتقل کند.
* فرمت خطای API را به شکل زیر استاندارد کند:

```json
{
  "status": 400,
  "message": "Validation failed.",
  "errors": {},
  "traceId": "..."
}
```

# مدیریت خطا

بک‌اند همیشه خطاها را با ساختار زیر برمی‌گرداند:

```json
{
  "status": 400,
  "message": "Validation failed.",
  "errors": {
    "fieldName": ["error 1", "error 2"]
  },
  "traceId": "..."
}
```

اگر امکان داشت، `errors` را به‌صورت خطای مربوط به همان فیلد نمایش دهید.

در غیر این صورت از `message` استفاده کنید.

# جریان احراز هویت

1. ایجاد حساب:

```http
POST /api/auth/register
```

2. ورود:

```http
POST /api/auth/login
```

این Endpoint پاسخ زیر را برمی‌گرداند:

```text
{ accessToken, expiresAt, user }
```

3. `accessToken` را در حافظه یا `localStorage` ذخیره کنید.

4. در تمام درخواست‌های محافظت‌شده Header زیر را ارسال کنید:

```text
Authorization: Bearer <token>
```

5. پس از منقضی شدن Token، که ۲۴ ساعت اعتبار دارد، کاربر باید دوباره Login کند.

# Endpointهای موجود

| متد    | Endpoint                 | احراز هویت | کاربرد                                            |
| ------ | ------------------------ | ---------- | ------------------------------------------------- |
| POST   | `/api/auth/register`     | خیر        | ایجاد حساب                                        |
| POST   | `/api/auth/login`        | خیر        | دریافت JWT Token                                  |
| GET    | `/api/transactions`      | بله        | دریافت لیست تراکنش‌ها با فیلتر، Pagination و Sort |
| GET    | `/api/transactions/{id}` | بله        | دریافت یک تراکنش                                  |
| POST   | `/api/transactions`      | بله        | ایجاد تراکنش                                      |
| PUT    | `/api/transactions/{id}` | بله        | ویرایش تراکنش                                     |
| DELETE | `/api/transactions/{id}` | بله        | حذف تراکنش                                        |
| GET    | `/api/categories`        | بله        | دریافت دسته‌بندی‌های عمومی                        |
| GET    | `/api/dashboard/summary` | بله        | اطلاعات تجمیعی Dashboard؛ در حال توسعه            |

قرارداد کامل API در فایل زیر قرار دارد:
